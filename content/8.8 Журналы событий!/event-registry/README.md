# Реестр событий

Каталог содержит Реестр событий РСУ и его представления для аналитиков, разработчиков и тестировщиков.

## Состав

- [[content/8.8 Журналы событий!/event-registry/Реестр событий]] — точка входа и сводное представление;
- `Реестр событий.base` — фильтруемое представление Реестра в Obsidian;
- `events/**/*.md` — карточки событий, сгруппированные по функциональным областям;
- [[content/8.8 Журналы событий!/event-registry/Реестр событий - правила]] — правила заполнения и согласования Реестра;
- `registry.schema.json` — схема данных, формируемых из карточек;
- `viewer/index.html` — интерактивное представление для сайта Quartz;
- `viewer/events.json` — данные интерфейса и интеграционный артефакт; вручную не редактируются.

## Принцип хранения

Нормативным источником являются Markdown-карточки из `events/`. Краткие индексируемые сведения хранятся в properties карточки, а триггеры, поля, сообщения и нормативное соответствие — в ее Markdown-разделах.

Файл `events.json`, интерактивный интерфейс и тестовые выборки должны формироваться из карточек автоматически после проверки структуры.

Реестр является спецификацией продукта и версионируется совместно с требованиями. База данных интерфейса просмотра не является первичным источником.

## Трассировка

Каждая карточка события содержит property `requirements` и таблицу «Связанные требования» со стабильными идентификаторами BR, FEAT и SR. Ссылки на пути и заголовки Obsidian используются только для навигации.

Для события в статусе `approved` должна существовать как минимум одна ссылка на системное требование `SR-...`. В соответствующем системном требовании должна присутствовать строка:

`**Регистрируемые события:** EVT-XXX-000 (success, access_denied)`

Автоматическая проверка должна подтверждать двустороннюю связь:

1. каждый SR из записи Реестра существует в требованиях;
2. SR содержит код события в атрибуте «Регистрируемые события»;
3. каждый код события из SR существует в Реестре;
4. указанные в обеих сторонах исходы события совпадают.

## Статусы записей

- `draft` — запись разрабатывается; ссылка на SR может отсутствовать;
- `review` — запись подготовлена к проверке; выявленные пробелы трассировки блокируют согласование;
- `approved` — запись согласована и может использоваться разработчиками и тестировщиками;
- `deprecated` — событие больше не формируется новыми версиями РСУ, но код сохраняется для чтения исторических данных.

Пилотные записи перенесены из старой Markdown-заготовки и имеют статус `draft`, поскольку исходные системные требования раздела настроек безопасности отсутствуют в текущей ветке.
