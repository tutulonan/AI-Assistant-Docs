
### BR-881-000 Единая модель данных событий аудита

Источники:

- ГОСТ Р 59547-2021 "Защита информации. Мониторинг ИБ",
- Приказ ФСТЭК России от 25.12.2017 № 239 (мера АУД.4),
- Методический документ ФСТЭК России от 12.04.2026 «Состав и содержание мероприятий и мер по защите информации, содержащейся в информационных системах» (РСБ.1, РСБ.4),
- Спецификация Micro Focus ArcSight Common Event Format (CEF v26-v27).

Ревизия: 06.2026

Для обеспечения сквозного контроля действий персонала, возможности расследования инцидентов безопасности, анализа технологических аварий и интеграции с внешними SIEM-системами все события в РСУ должны фиксироваться по единой стандартизированной модели данных.  
Унификация структуры события исключает появление "слепых зон" при аудите и позволяет применять единые алгоритмы фильтрации, поиска и экспорта данных вне зависимости от того, в какой подсистеме (АРМИ, АРМО, серверные службы) произошло действие.

### BR-881-001 Прослеживаемость контекста действия ("Кто, Где, Когда, Что")

**Источник:** ГОСТ Р МЭК 62443-3-3-2016 (SR 2.12; обязательность зависит от целевого уровня безопасности SL).

**Ревизия:** 23.09.2026

Каждая запись аудита должна обеспечивать принцип неотрекаемости (Non-repudiation) и содержать исчерпывающий контекст:

1. Временной контекст: когда действие было инициировано пользователем и когда фактически зафиксировано в БД;
2. Субъект действия: кто совершил операцию (логин, ФИО, статус учетной записи на момент действия);
3. Физическая локализация: с какого рабочего места (IP-адрес и сетевое имя АРМ) отправлена команда;
4. Объект и суть воздействия: в каком модуле, над каким объектом, какой параметр был изменен, старое и новое значения, а также итоговый результат операции.

### BR-881-002 Защита конфиденциальных данных в записях аудита

**Источники:** Приказ ФСТЭК России № 239 (АУД.6); Методический документ ФСТЭК России от 12.04.2026 (РСБ.4).

**Ревизия:** 23.09.2026

Журнал аудита не должен становиться источником утечки аутентификационных данных. Система должна гарантировать, что пароли пользователей, секретные ключи и коды восстановления ни при каких обстоятельствах (включая ошибки валидации или сбои) не сохраняются в открытом или обратимо зашифрованном виде в полях событий и текстах сообщений.

### BR-881-003 Соответствие состава регистрационной записи требованиям ГОСТ Р 59548-2022

**Источники:**
- ГОСТ Р 59548-2022 (пп. 6.1.1–6.1.3, таблицы 1–3),
- ГОСТ Р 59548-2022 (пп. 6.2.1, 6.2.4, 6.2.6–6.2.8, 6.2.34–6.2.36, 6.2.50, 6.2.52–6.2.55).

**Ревизия:** 22.09.2026

Единая модель события и физические структуры таблиц `events_operational` и `audit_security` должны обеспечивать регистрацию обязательной информации о событиях безопасности, установленной ГОСТ Р 59548-2022.

Для каждого события безопасности система должна обеспечивать определение следующих нормативных элементов:

1. дата и время события;
2. уникальный код события безопасности;
3. краткое наименование события;
4. субъект доступа;
5. тип события безопасности по ГОСТ Р 59548-2022;
6. уровень важности события.

Тип события безопасности по ГОСТ Р 59548-2022 не хранится в отдельном поле физической записи. Он должен однозначно определяться по `event_code` через системный Реестр событий. Для каждого кода события ИБ в Реестре должны быть заданы применимый тип, ссылка на пункт ГОСТ и обязательный состав дополнительных параметров. Связь `event_code` с типом события после ввода кода в эксплуатацию не должна изменяться.

### BR-881-005 Нормативные правила представления значений

**Источник:** ГОСТ Р 59548-2022 (п. 6.1.1, таблица 1; п. 6.1.2, таблица 2).

**Ревизия:** 22.09.2026

1. Значения `event_time` и `recorded_time` должны храниться с часовым поясом. При экспорте события дата и время должны представляться в формате `YYYY-MM-DDThh:mm:ss[.sss]±hh:mm`.
2. Для поля `severity` устанавливается следующее соответствие внутренних уровней РСУ уровням важности ГОСТ:

| Уровень РСУ | Уровень важности по ГОСТ Р 59548-2022 |
| --- | --- |
| `INFO` | низкий |
| `WARN` | средний |
| `ERROR` | высокий |
| `CRITICAL` | критический |

Уровни «аварийный», «фатальный» и «отладочный» в текущем наборе событий РСУ не используются. При появлении событий, требующих таких уровней, перечень значений `severity` и правила отображения должны быть расширены до ввода соответствующих кодов событий в эксплуатацию.
3. Для событий безопасности поля, имеющие статус «Обязательное», не должны содержать `NULL`. Исключение составляет субъект доступа, если он объективно не может быть определен для конкретного типа события в соответствии с ГОСТ.
4. Условно обязательные поля могут содержать `NULL` только тогда, когда соответствующий элемент не применяется к типу события, определенному в Реестре событий.
5. Обязательные по ГОСТ сведения должны храниться в отдельных полях события либо в структурированном наборе дополнительных параметров. Допускается повторение этих сведений в поле message, однако извлечение обязательных данных путем анализа текста сообщения не допускается.

## 1. Дата и время события

**Идентификатор в БД:** event_time

Формируется клиентским приложением (АРМИ/АРМО) в момент инициации действия пользователем, отображается в локальном часовом поясе клиента в формате ДД.ММ.ГГГГ ЧЧ:ММ:СС.МММ.

## 2. Дата и время записи

**Идентификатор в БД:** recorded_time

Формируется СУБД автоматически в момент сохранения записи в базу данных в формате UTC. Служит для выявления задержек доставки событий и анализа временных коллизий.

## 3. Источник

**Идентификатор в БД (Key):** source_app

Формируется автоматически клиентским приложением или службой в момент генерации события. Указывает конкретный программный компонент РСУ, в котором зародилось действие.

Принимает следующие значения:
- **АРМИ** — действие совершено пользователем в среде разработки (АРМ Инженера);
- **АРМО** — действие совершено оператором на мнемосхемах или панелях среды исполнения (АРМ Оператора);
==Уточнить другие источники==
- ==**Сервер** — событие сгенерировано серверными сервисами (Сервер Истории, Сервер Проектов);==
- ==**ПЛК** — событие сгенерировано напрямую рантаймом контроллера;==
- ==**Служба** — фоновая системная служба (сервис лицензирования, сервис синхронизации времени и др.).==

## ==4. Рабочая станция==

==**Идентификатор в БД (Key):** workstation  

==Формируется автоматически сетевым стеком приложения в момент отправки запроса. Фиксирует сетевое имя узла и его IP-адрес (IPv4 или IPv6), с которого пользователь выполнил операцию.==

==Форматируется в виде: <Имя_АРМ> (<IP-адрес>) (например: ARM-ENG-01 (192.168.10.15)). Для чисто серверных фоновых событий без участия рабочей станции указывается имя сервера и его локальный адрес.==

==Служит для обеспечения физической прослеживаемости точки воздействия и расследования инцидентов ИБ.==


## 5. Результат

**Идентификатор в БД (Key):** outcome  

Формируется сервером автоматически по результатам обработки транзакции. Фиксирует итоговую успешность выполнения действия и базовую категорию отклонения.

Принимает следующие значения:

- **Успех** — операция успешно проверена, валидирована и сохранена в системе;
- **Неуспех (Отказ в доступе)** — действие заблокировано системой безопасности из-за отсутствия необходимых прав доступа или недостаточного уровня администрирования (SEC-LVL) (триггер и конкретные права на каждое действие указывается в реестре);
- **Неуспех (Ошибка валидации)** — действие отклонено из-за нарушения правил бизнес-логики и ограничений проекта при вводе данных (триггер указывается в реестре);
- **Неуспех (Ресурс занят)** — действие отклонено из-за блокировки целевого объекта другим пользователем или системным процессом. Этот результат возможен только, если ресурс вообще может быть занят);
- **Неуспех (Системный сбой)** — действие прервано из-за внутренней технической ошибки сервера, базы данных или сети. Сюда так же попадают события, не попавшие в остальные причины неуспеха.

Примечание: Детальное текстовое пояснение с точной причиной отказа подставляется в поле 17 ("Сообщение").

## 6. Пользователь (Логин)

**Идентификатор в БД (Key):** user_login  

Формируется автоматически сервисом аутентификации в момент совершения действия. Фиксирует уникальный системный логин учетной записи, от имени которой было инициировано действие.

Правила формирования и хранения:
- Хранится в открытом текстовом виде (является открытым идентификатором субъекта в стандартах аудита и CEF).
- Для автоматических системных действий (выполненных сервисами без прямого участия человека) в поле автоматически записывается значение **Система**.
- Для действий, совершенных до этапа авторизации (например, запуск АРМ в режиме "Гость"), фиксируется логин соответствующей гостевой учетной записи.

## 7. ФИО

**Идентификатор в БД (Key):** user_fullname  

Формируется автоматически на основе данных профиля пользователя в момент совершения действия. 

Правила формирования и отображения:
- Если у учетной записи не заполнено поле ФИО (например, для встроенной учетной записи Administrator или сервисных аккаунтов), в поле записывается прочерк —.

## 9. Действие

**Идентификатор в БД (Key):** action_name  

Формируется на основе карточки события из Реестра событий (EVT-XXXXX). Фиксирует стандартизированное краткое наименование выполненной или запрошенной операции.

Правила формирования и отображения:
- Записывается строго в формате отглагольного существительного (например: Запуск процесса развертывания, Сброс пароля пользователя, Создание роли, Авторизация пользователя).
- Не содержит переменных данных, динамических путей или значений параметров (все динамические подробности передаются в поля "Расположение", "Значение" и "Сообщение").
- Отображается по умолчанию во всех пользовательских журналах (Инженера, Оператора, ИБ).
- Является ключевым полем для быстрой группировки, сортировки и построения аналитических отчетов.

## 10. Критичность (Важность)

**Идентификатор в БД (Key):** severity  

Формируется на основе уровня, заданного аналитиком в Реестре событий, с учетом системных правил динамической эскалации при возникновении инцидентов. Определяет степень риска события для непрерывности технологического процесса, целостности проекта и информационной безопасности РСУ.

Принимает следующие стандартизированные значения:
- **INFO** (Информация / Низкая) — штатные действия пользователей в оффлайн-редакторах (Design-time), успешная аутентификация и завершение сеанса, чтение данных, просмотр мнемосхем и трендов;
- **WARN** (Предупреждение / Средняя) — ошибки валидации данных при вводе, единичные неверные вводы паролей (до лимита блокировки), отказ в выполнении действия из-за занятости ресурса другим пользователем;
- **ERROR** (Ошибка / Высокая) — развертывание проекта (Deploy) в контроллер, изменение параметров рантайма в онлайн-режиме, автоматическая блокировка УЗ, а также **любые события со статусом "Неуспех: Отказ в доступе"** (повышаются системой автоматически);
- **CRITICAL** (Критическая) — события наивысшего приоритета: заводской сброс или полная очистка памяти ПЛК, откат проекта из контрольной точки (Disaster Recovery), изменение прав ролей безопасности, очистка и автоматическая ротация базы данных Журнала ИБ.

В интерфейсе Журналов отображается по умолчанию с цветовой индикацией.

## 11. Область действия

**Идентификатор в БД (Key):** scope  

Определяет функциональную подсистему, инженерный модуль или конкретную экранную форму (мнемосхему), в границах которой произошло событие.

Правила формирования значения:
##### 1. Для среды разработки (АРМИ):

Значение задается из Реестра событий и принимает строго один из фиксированных системных модулей:
- **аппаратная конфигурация** — действия с деревом устройств, крейтами, модулями ввода-вывода, сетевыми интерфейсами и протоколами обмена (HART, Modbus, Profibus);
- **программная конфигурация** — действия в дереве программных объектов, редакторах CFC/ST, связях, параметрах, шаблонах и экземплярах ФБ/КУ;
- **HMI** — проектирование и верстка экранных форм, мнемосхем, графических символов и примитивов в среде IDE;
- **менеджер развертывания** — операции сборки, валидации компонентов и загрузки (Deploy) конфигурации в память контроллеров;
- **менеджер пакетов** — добавление, удаление, экспорт и обновление версий контент-пакетов (КП) и библиотек проекта;
- **менеджер лицензий** — управление аппаратными и программными лицензиями проекта;
- **контрольные точки** — создание, экспорт, переименование и откат (восстановление) проекта из контрольных точек;
- **безопасность** — события авторизации, аутентификации, управления жизненным циклом пользователей, ролями, правами доступа, а также любые попытки несанкционированного доступа;
- **система** — автоматические или общие действия системы, которые не относятся к какому-то конкретному модулю (например: автоматическое освобождение занятого ресурса по тайм-ауту).

#### 2. Для среды исполнения (АРМО):

- **<Имя формы/мнемосхемы>** — если событие вызвано взаимодействием оператора с графическим элементом (клапаном, насосом, полем ввода уставки, кнопкой управления), в поле автоматически подставляется имя текущей открытой экранной формы (например: Мнемосхема_Котельная_1, Форма_Управление_Н1);
- **безопасность** — события авторизации/выхода оператора на рабочей станции, автоматическая блокировка сеанса по таймауту бездействия, ошибки ввода пароля, подтверждение защищенных уставок;
- **система** — автоматические или общие действия на станции оператора, которые не связаны с открытием или работой конкретной мнемосхемы.


**Список "Областей действия" может пополняться по мере написания требований к новым модулям системы.**

## 12. Журналы

**Идентификатор в БД (Key):** journal_mask  

Поле определяет, в каких именно пользовательских интерфейсах РСУ (пресетах) должно отображаться событие, и выступает в роли правила для определения, в какую физическую таблицу базы данных (или в обе сразу) должна быть направлена транзакция.

**Формирование:** задается аналитиком в Реестре событий, вычисляется бэкенд-роутером до момента сохранения в БД.
**Отображение в UI:** служебное поле (скрыто на экране). Используется СУБД для фильтрации записей на соответствующих вкладках интерфейса.
 
Правила формирования и логика работы:

**Варианты назначения аналитиком в Реестре:**
- **Статическое (без условий):** журналы перечисляются через запятую (например: Журналы: Журнал Инженера, Журнал Оператора).
- **Условное (с ветвлением):** целевой журнал зависит от контекста выполнения (например: Журналы: Журнал ИБ, Журнал Инженера (ЕСЛИ Источник == "АРМИ") / Журнал Оператора (ЕСЛИ Источник == "АРМО")).

**Момент вычисления:**
Все условия (ЕСЛИ) вычисляются бэкендом **строго ДО момента записи события в базу данных**. В БД сохраняется готовое итоговое число битовой маски.

**Архитектура 3-битовой маски:**
В кодовой базе бэкенда Реестр событий хранится в виде статического конфигурационного справочника (JSON / YAML / код), где каждому событию EVT-XXXXX сопоставлено числовое значение маски journal_mask:
- **Бит 0** (числовой вес **1** / 001) = **Журнал Инженера**
- **Бит 1** (числовой вес **2** / 010) = **Журнал Оператора**
- **Бит 2** (числовой вес **4** / 100) = **Журнал ИБ**

Таблица значений битовой маски:

| Маска (journal_mask) | Двоичный вид | Целевые журналы (Где отображается)          | Пример события                                         |
| -------------------- | ------------ | ------------------------------------------- | ------------------------------------------------------ |
| **1**                | 001          | **Только Журнал Инженера**                  | Рутинное ФБ в схеме                                    |
| **2**                | 010          | **Только Журнал Оператора**                 | Рутинное переключение на мнемосхеме АРМО               |
| **3** (1 + 2)        | 011          | **Журнал Инженера + Журнал Оператора**      | Изменение settable-параметра онлайн с АРМИ             |
| **4**                | 100          | **Только Журнал ИБ**                        | Фоновая автоблокировка УЗ при превышении попыток входа |
| **5** (1 + 4)        | 101          | **Журнал Инженера + Журнал ИБ**             | Восстановление проекта из Контрольной точки            |
| **6** (2 + 4)        | 110          | **Журнал Оператора + Журнал ИБ**            | ==Заводской сброс контроллера ПЛК==                    |
| **7** (1 + 2 + 4)    | 111          | **Все 3 журнала (Инженер + Оператор + ИБ)** | Запуск процесса развертывания                          |

**Алгоритм диспетчеризации по физическим таблицам (До записи в БД):**
Сервис логирования в оперативной памяти вычисляет итоговую маску события и направляет запись по соответствующим таблицам в рамках единой транзакции СУБД:
1. **Если установлен Бит 2 (вес 4, Журнал ИБ):**
    - Сервер выполняет INSERT в изолированную таблицу безопасности (режим WORM).
    - В самой таблице audit_security колонка маски не требуется, так как 100% записей в ней принадлежат аудиту безопасности.
    
2. **Если установлен Бит 0 (вес 1) или Бит 1 (вес 2):**
    - Сервер выполняет INSERT в общую таблицу для Журналов Оператора и Инженера (срок хранения 90 дней).
    - В колонку journal_mask этой таблицы сохраняются биты 1, 2 или 3, что исключает дублирование строк при совместных технологических событиях.

3. **Если установлены и биты операций (1/2), и бит ИБ (4) — маски 5, 6, 7 (Dual Write):**
    - Сервер параллельно вставляет запись в обе таблицы (events_operational и audit_security) с общим идентификатором сквозной корреляции correlation_id (UUID).


**Системное спец-правило:**
Если любое действие в системе завершается с результатом **"Неуспех: Отказ в доступе"**, бэкенд до записи в БД **всегда автоматически добавляет Бит 2 (mask = mask | 4, Журнал ИБ)**, независимо от исходно заданных правил.

- **Формирование:** Автоматически (считывается системой до применения изменений)
- **Отображение в UI:** Отображается по умолчанию в Журнале Инженера и Журнале Оператора

**Описание и правила формирования:**
Фиксирует состояние или значение настраиваемого поля **до момента выполнения операции**.
1. **Правило маскирования секретных данных:**
    - При любых операциях с паролями, пин-кодами и криптографическими ключами в поле **всегда строго записывается прочерк —**.
    
2. **Форматирование значений:**
    - ==Для технологических параметров и таймеров сохраняется значение вместе с единицами измерения (например: 10 мин, 50.0 %, 2 сек, 25.5 °C).==
    - Логические параметры (Boolean) преобразуются в человекочитаемый вид: Включено или Отключено.
    - При изменении сложных списков или наборов прав передается список до изменения либо —.

3. **Для операций создания:**
    - При создании нового объекта или первоначальной установке свойства (когда старого значения не существовало) записывается прочерк —.

## 16. Значение

- **Идентификатор в БД (Key):** new_value 

- **Формирование:** Автоматически (сохраняется установленное значение).
- **Отображение в UI:** Отображается по умолчанию в Журнале Инженера и Журнале Оператора.

**Описание и правила формирования:**
Фиксирует новое состояние или значение настраиваемого поля **после выполнения операции**.
1. **Правило маскирования секретных данных:**
    - При любых операциях с паролями, пин-кодами и криптографическими ключами в поле **всегда строго записывается прочерк —**.

2. **Форматирование значений:**
    - Для технологических параметров и таймеров сохраняется значение вместе с единицами измерения (например: 10 мин, 50.0 %, 2 сек, 25.5 °C).
    - Логические параметры (Boolean) преобразуются в человекочитаемый вид: Включено или Отключено.
    
3. **Для операций удаления:**
    - При удалении объекта или сбросе свойства в пустое состояние записывается прочерк —.

    - Фиксирует значение, которое пользователь **пытался установить** (если это применимо), либо прочерк —.

## 17. Сообщение

- **Идентификатор в БД (Key):** message

- **Формирование:** Из Реестра событий (динамическая сборка из шаблона с подстановкой фактических значений переменных).
- **Отображение в UI:** Отображается по умолчанию во всех журналах (Инженера, Оператора, ИБ). Является главным информационным полем строки события.

**Описание и бизнес-смысл:**
Полный человекочитаемый текст события, содержащий исчерпывающее словесное описание выполненного действия или причины его блокировки. Формируется бэкендом на основе шаблонов из Реестра событий (EVT-XXXXX).

##### Правила формирования текста:
Ветвление по исходу операции:

- **При успешном выполнении (Успех):**
    - Текст формируется по шаблону ветки **При успехе** из Реестра событий с подстановкой фактических параметров действия.
    - Пример: Пользователь 'petrov_ii' изменил параметр 'Уставка SP' в блоке 'App_1/Circuit_1/PID_1' с '50.0' на '75.5'.

- **При неуспешном выполнении (Неуспех):**
    - **При отказе в доступе:** формируется по шаблону При отказе в доступе:
        - Пример: Отклонено удаление роли 'Administrator': недостаточно прав.

    - **При ошибке валидации:** формируется по шаблону При ошибке валидации с подстановкой текста сообщения из нарушенного правила валидации:
        - Пример: Отклонено создание пользователя 'j.doe': учетная запись с таким логином уже существует.

    - **При занятости ресурса:** формируется системное сообщение:
        - "Действие не выполнено: ресурс занят."
    
	- **При техническом сбое (системной ошибке):** формируется стандартизированное общее сообщение без технических подробностей:
	    - "Действие не выполнено: системный сбой."
    

Поле "Сообщение" участвует в глобальном поиске по Журналу (пользователь может найти событие по любому фрагменту фразы или имени переменной).
